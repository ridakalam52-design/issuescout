#143 Cached exception colors leak into no_color and standard formatters

bugP1colorlogexceptionformatterbug

Why: The issue breaks core logging functionality by leaking colored exception formatting into non-color contexts due to shared caching of exception text.

Guardrail: safe (meta-llama/Llama-Guard-4-12B)

Repro (Otari sandbox, deepseek-ai/DeepSeek-V4.1-Flash-1017): reproduced: After formatting with force_color, the no_color formatter's output still contains ANSI escapes (e.g. '\x1b[35m' in the traceback), so the assertion fails with AssertionError.

Related docs / known fixes:

Draft reply

Thanks for the detailed report and the minimal repro — very helpful. I ran the repro in IssueScout's sandbox (not on a maintainer's machine), and it reproduces: after the `force_color` formatter runs, the `no_color` formatter's output still contains ANSI escapes (e.g. `\x1b[35m` in the traceback), so the assertion fails with `AssertionError`. I've triaged this as a P1 bug under the `colorlog`/`exception`/`formatter` labels. Your diagnosis matches what I see: `logging.Formatter.format` caches `formatException` output in `record.exc_text`, and that cache is shared across handlers even though traceback coloring is per-formatter. The usual workaround is to clear the cache per formatter (e.g. `record.exc_text = None` before formatting, or override `format` to avoid reusing `exc_text`). No upstream fix is confirmed yet. Useful references: the Python logging docs on `Formatter.format`/`exc_text` caching (https://docs.python.org/3/library/logging.html) and the upstream repo (https://github.com/borntyping/python-colorlog). To confirm scope: does this also occur when the two formatters are attached to separate handlers on the same logger, and on Python 3.12 or earlier?
